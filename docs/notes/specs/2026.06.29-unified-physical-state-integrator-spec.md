# ECS Spec: Unified Physical State + Single Integrator — No Exemptions

**Status:** IMPLEMENTED. Supersedes the barrier/exemption parts of
`2026.06.26-ecs-double-buffer-single-writer-spec.md` (its §3 Rule 3 "discrete
event" row, §4 "Barrier systems … exempt from single-writer", §5 recenter
fallback, and §6 in full). The Jacobi snapshot rule and the force-accumulator
idea from that spec are KEPT and generalized; the "serial barrier, exempt from
the rule" tier is DELETED.
**Date:** 2026-06-29
**Scope:** the per-tick update discipline for the single ECS substrate.
See `[[no-barrier-exemptions]]`, `[[ecs-double-buffer-single-writer]]`,
`[[single-ecs-substrate]]`.

---

## 0. The one sentence

There is **one** writer of physical state — an integrator that owns a single
`:component/physical` and reads, each tick, the previous snapshot plus a set of
**influence components** registered against the physical fields they affect;
every other system is a pure, snapshot-reading, single-component-writing emitter,
and **nothing runs serially "after the fold."** No exemptions.

---

## 1. Why this exists (the magic word)

The prior spec established the right rule — Jacobi snapshot, single writer per
component — then carved a hole in it: a "barrier" tier that "runs serially after
the fold" and "may write anything." That word became an excuse. The audit
(2026-06-29):

- The invariant checker is **complicit**: `registry/fan-out-systems` strips every
  `:stage :barrier` system *before* `write-conflicts` runs, so
  `assert-single-writer!` is structurally blind to the violations it should catch.
- Removing that filter surfaces four real conflicts hidden behind it:

  | Component | Co-writers |
  |---|---|
  | `composition` | `:nucleosynthesis`, `:deuterium-depletion` |
  | `spin` | `:em`, `:disk-evolution` |
  | `angular-momentum` | `:em`, `:disk-evolution` |
  | `position` | `:motion`, `:recenter` |

- A whole tier is **off the registry entirely** (never checked): `sink-formation`,
  `stellar-wind`, `stellar-flare`, `fusion-promotion`, `apply-thermal-interventions`,
  `observer-system`, and the pacing/clock scalar.
- Several `:barrier` systems are pure cargo-cult — `xuv-atmospheric-escape`,
  `lod-scheduler`, `magnetosphere-coupling` each write only their own component and
  only do cross-entity *reads* (which Jacobi allows). They were barriered for no
  reason the rule forbids.

**The rule has no exemptions.** This spec defines the single model every one of
these collapses into.

---

## 2. The rule, restated (unchanged, absolute)

1. **Snapshot read / private write (Jacobi).** A tick reads world *N* (immutable,
   shared) and produces *N+1*. No system observes another system's same-tick write.
   Permuting the system set is bit-identical.
2. **Single writer per component.** Every component type is written by exactly one
   system. A second writer is a **build failure**, enforced over ALL systems — no
   filter, no `:barrier` escape hatch.
3. **Contended values are decomposed, never co-written.** A value many systems want
   to affect is split into an owner + per-influencer **contribution components**.
   This spec makes that mechanism uniform and total (§3–§4).

The one-tick latency this imposes (a contribution emitted at *N* lands at *N+1*) is
**accepted** — the deliberate price of total order-independence.

## 3. The model: one physical component, one integrator

Generalize the old "velocity is an integrator, forces are contributions" from a
special case (force→velocity) to the whole of physics.

### 3.1 `:component/physical` — the one physical-state component

All genuine physical properties live in **one** component, read by anything that
needs them: `position`, `velocity`, `mass`, `temperature`, `density`, `radius`,
`angular-momentum`, `spin`, `b-field`, `frozen-flux`, `composition`, `luminosity`,
`pressure`, … (the migration, §6, moves today's separate components into fields of
this one). Everything reads these from the **snapshot**; that is the single source
of physical truth.

> Why one component, not many single-owned ones? Because the real owner is the same
> for all of them — *the integrator that applies last tick's influences while
> enforcing conservation*. Splitting physical state across many owners is what
> forced the cross-property barriers (disk writing `mass` AND `spin`; thermal
> writing `temperature` from interventions). One owner, one place for the
> conservation laws to live.

### 3.2 The integrator — sole writer of `:component/physical`

Each tick, for each entity, the integrator computes the next `:component/physical`
from (a) that entity's previous `:component/physical` in the snapshot and (b) every
**influence component** registered against a physical field (§4). It is the single
home of:

- **Accumulation** — Σ of additive influences into a field (Σ accel → velocity;
  Σ heat-flux → temperature; Σ torque → angular-momentum; Σ mass-flux → mass).
- **Derivation** — fields that are pure functions of other fields, not sums
  (`pressure = EOS(ρ,T)`; `spin = L/I`; `b-field = Φ/R²`; virial `temperature`).
  Computed from the snapshot's fields — mutual dependencies (radius↔density) become
  a stable cross-tick fixed point, exactly as the prior spec noted.
- **Conservation laws & invariants** — momentum/energy/mass/charge conservation,
  positivity, clamps, the c-limit on Δv. This is the natural and *only* place to
  enforce them, because it is the single point where all influences on a property
  combine. Conservation is enforced primarily by **construction** (influences are
  emitted in conservative, equal-and-opposite pairs, so a local per-entity sum is
  globally conservative — no global reduction needed); the integrator **asserts**
  the invariant and is the audit point if it ever fails.

The integrator is per-entity-parallel: entity *e*'s next physical state depends only
on *e*'s snapshot state and *e*'s influence components — all cross-entity coupling
(gravity, SPH, Lorentz, accretion) already happened in the influence emitters, which
are the expensive systems and stay in the parallel fan-out.

### 3.3 Influence emitters — the fan-out

Every other system is a pure emitter: reads the snapshot, writes **one** influence
component it solely owns. Gravity→`accel.gravity`, Hydro→`accel.pressure`,
EM→`accel.lorentz` + `torque.em` + `dBdt.em`, fusion→`heat.fusion`, accretion→
`mass-flux`/`momentum-flux`, observer→`accel.observer`, interventions→
`accel.warp`/`heat.intervention`, … all single-writer, all snapshot-read, all
order-irrelevant. These are exactly the systems that exist today; they just stop
writing physical state directly and write a named influence instead.

## 4. The influence registry

The integrator is configured by a **declarative registry** mapping each influence
component (and which field on it) to the physical field it influences and how it
composes. This is the literal "the influencing components and the field(s) on those
components which influence which physical property, registered with it."

```clojure
;; sketch — the integrator reads this, not hardcoded knowledge
{:component/accel.gravity   {:field :vec   :influences :velocity      :compose :sum :scale :dt}
 :component/accel.pressure  {:field :vec   :influences :velocity      :compose :sum :scale :dt}
 :component/accel.lorentz   {:field :vec   :influences :velocity      :compose :sum :scale :dt}
 :component/accel.observer  {:field :vec   :influences :velocity      :compose :sum :scale :dt}
 :component/accel.warp      {:field :vec   :influences :velocity      :compose :sum :scale :dt}
 :component/torque.em       {:field :vec   :influences :angular-momentum :compose :sum :scale :dt}
 :component/torque.disk     {:field :vec   :influences :angular-momentum :compose :sum :scale :dt}
 :component/heat.fusion     {:field :rate  :influences :temperature   :compose :sum :scale :dt}
 :component/heat.intervention {:field :rate :influences :temperature  :compose :sum :scale :dt}
 :component/mass-flux       {:field :rate  :influences :mass          :compose :sum :scale :dt}
 ...}
;; derived fields declare a pure fn of other :component/physical fields instead:
{:pressure          {:derive (fn [p] (eos (:density p) (:temperature p)))}
 :spin              {:derive (fn [p] (/ (:angular-momentum p) (moment-of-inertia p)))}
 :b-field           {:derive (fn [p] (flux->b (:frozen-flux p) (:radius p)))}}
```

Adding a new force/heat/torque source = define an emitter that writes a new
influence component + one registry line. No edit to the integrator body, no ordering
to reason about. `velocity` gaining a sixth contributor is one line, not a conflict.

## 5. Entity lifecycle is NOT a single-writer concern

The reframing that dissolves the old "Category D" barrier:

> **A component (or entity) created this tick cannot be influenced by anything that
> also happened this tick — it is only visible once the next tick's snapshot
> contains it.** So creation is *automatically* Jacobi-consistent. There is no
> contended write, hence no rule to exempt.

- **Spawn.** A system requesting a new entity/component emits that request in its
  write-set; the fold materializes it into world *N+1*. Every system this tick read
  a snapshot without it; next tick everyone sees it. No conflict, no barrier.
- **Despawn.** The mirror image: an entity omitted from *N+1* was fully present in
  *N*'s snapshot, so every this-tick reader was consistent; next tick it is simply
  absent. Removal is a world-construction step, not a component write — provided the
  *decision* to remove is a single-owner act (the entity marks itself consumed, or
  one owner emits the removal). No contended continuous-state write occurs.
- **Merge (N→1 mass/momentum transfer).** The only part that touches contended
  state, and it is just an influence: the absorbing body receives a `mass-flux` /
  `momentum-flux` contribution (single-writer, snapshot-read, conservative pair),
  integrated next tick like any force. The absorbed body marks itself consumed and
  is reaped from *N+1*. `mass` becomes an accumulated physical field exactly like
  `velocity`.

So collision, sink accretion, stellar-wind mass loss, fusion-promotion — none need a
serial barrier. Mass changes flow through the integrator as influences; lifecycle
changes flow through world-construction and are Jacobi-safe by the visibility rule.

## 6. How each audit finding maps onto this model

| Today (violation) | Becomes |
|---|---|
| `xuv-escape`, `lod-scheduler`, `magnetosphere` `:stage :barrier` | drop the marker — plain fan-out emitters (already single-writer, cross-entity *reads* are legal) |
| `composition`: nucleosynthesis + deuterium | both emit influences (`burn-rate`, `depletion-rate`) → integrator owns `composition` |
| `spin`/`angular-momentum`: em + disk | both emit `torque.*` → integrator owns `angular-momentum`; `spin` is derived `L/I` |
| `position`: motion + recenter | integrator owns `position`; recenter is a `frame-offset` influence from the previous snapshot's COM (one tick stale = pure Galilean shift), not a post-fold write |
| `disk-evolution` writing `mass` | `mass-flux` influence → integrator owns `mass` |
| `apply-observer-influence` (serial in `tick-world`) | already emits `accel.observer`; just run it as a fan-out emitter off the snapshot |
| `apply-thermal-interventions` (writes temperature serially) | emit `heat.intervention` → integrator owns `temperature` |
| collision / sink-formation / wind / flare (serial despawn+merge) | influences (`mass-flux`/`momentum-flux`) + consumed-marker reaped at world-construction (§5) |
| pacing/clock scalar + time-slip (orchestrator-tier) | a `:sim/dt` owner system reading the previous snapshot's bulk state + observer coherence; world-scalar, one writer (see Open Questions) |
| `fan-out-systems` filter hiding barriers from the check | **deleted** — `write-conflicts` runs over ALL systems |

## 7. Migration sequence

1. **Make the checker honest.** Delete the `:barrier` filter in `fan-out-systems`;
   register the off-book systems. The build now FAILS on every real violation — the
   true blast radius, enforced not aspirational. (Expect the four conflicts in §1
   plus the unregistered tier to light up.)
2. **Cargo-cult barriers.** Drop `:stage :barrier` from xuv/lod/magnetosphere.
3. **Introduce `:component/physical` + the integrator + registry** alongside the
   existing components; integrator initially owns only `position`/`velocity` (port
   Motion) to prove the registry path end-to-end.
4. **Observer + thermal** → `accel.observer` runs in the fan-out; interventions emit
   `heat.intervention`. (Smallest real contribution+integrator cases; the observer
   already half-does it.)
5. **Fold derivations & the remaining accumulators** into the integrator:
   composition (burn/depletion), rotation (torques), mass (mass-flux),
   pressure/spin/b-field/temperature as derived fields.
6. **recenter** → frame-offset influence.
7. **Lifecycle** → merge/despawn as influence + consumed-marker reaped at
   world-construction (§5); retire the serial `step-physics` chain.
8. **Delete** the Gauss–Seidel `physics-systems` path once the integrator forms a
   star (the open content item from the prior spec §10).

Each step keeps a green build and a strictly-shrinking conflict count.

## 8. Open questions (need a decision)

- **World scalars (`:sim/dt`, pacing, COM).** These are global reductions, not
  per-entity components. Cleanest fit: a single-owner "world system" that reads the
  *previous* snapshot's reduction and writes the scalar for next tick — same
  one-tick-stale discipline as the frame-offset. Confirm this is the intended home
  rather than the orchestrator. (The time-slip wiring just added lives here.)
- **Integrator granularity.** One function with a registered field-map, vs. a set of
  per-field updaters that share the `:component/physical` owner. Both satisfy
  single-writer (the *component* has one owner); the latter keeps each field's logic
  isolated. Leaning per-field-updater behind one owner.
- **Conservation coupling across merges.** The "conservative-by-construction
  influence pairs" claim (§3.2) needs verifying for the N→1 accretion case — does a
  single `momentum-flux` onto the survivor, paired with the consumed body's removal,
  conserve exactly, or is a per-merge reduction unavoidable? If the latter, it is
  still expressible as an influence emitted at *N*, integrated at *N+1* — not a
  barrier.

## 9. Non-goals

- Not changing physics formulas — only *which system owns which write* and *where
  the formula reads its inputs* (snapshot, always).
- Not removing the ledger/rewindability — discrete events still record to the ledger
  as facts; this spec only removes their license to *write contended state serially*.
- Not lock-free beyond snapshot/private-buffer + the one end-of-tick fold.
