## Best-fit stack

For rendering, the two serious bases are raw OpenGL/Vulkan through LWJGL or bgfx through LWJGL bindings, because LWJGL exposes both the graphics APIs and bgfx bindings in a low-level form. For math, JOML is the obvious fit because it is small, fast, buffer-friendly, multi-thread-capable, and allocation-free by design for the common path. For dev UI and in-engine tools, Nuklear is a cleaner fit than a higher-level retained UI when you want the renderer to stay sovereign, and the Clojure/LWJGL example shows exactly that style of integration.[^2_3][^2_4][^2_5][^2_6][^2_7][^2_8][^2_2]

That yields a stack like this:

- Core runtime: Clojure JVM.
- Native boundary: LWJGL for GLFW, OpenGL or Vulkan, STB, optional bgfx.[^2_2][^2_3]
- Math: JOML.[^2_6][^2_8]
- Debug/editor UI: Nuklear via LWJGL, not your main rendering path.[^2_4][^2_7]
- Physics: mostly custom for orbital mechanics; Bullet bindings only for local rigid-body/contact problems if you need them later.[^2_9][^2_10][^2_11]


## OpenGL vs bgfx

If your instinct is “I want exact control over GPU work,” raw OpenGL through LWJGL is still the cleanest first target, because it minimizes indirection and matches your prior WebGL mental model closely. bgfx is attractive if you want backend portability across Direct3D, Metal, Vulkan, and OpenGL without personally owning each backend, and LWJGL exposes bgfx plus tooling such as `shaderc`.[^2_12][^2_13][^2_1][^2_3][^2_2]

My interpretation:

- Pick **OpenGL first** if you want the shortest path from your WebGL instincts to a working optimized renderer, especially for custom voxel meshing, sparse streaming, and specialized shader passes.[^2_1][^2_2]
- Pick **bgfx** if cross-platform backend insulation matters early and you accept a little abstraction tax in exchange for portability.[^2_12][^2_3]

For a small team or solo engine with “performance is absolute, time is available,” I would start OpenGL, establish engine contracts, then consider a bgfx branch only if backend pain becomes real. That keeps category and contract boundaries honest: first prove the data model and frame graph, then pay portability tax only when warranted.

## ECS guidance

The available Clojure ECS libraries look lightweight rather than battle-proven at the scale you’re aiming for, with `clj-ecs` describing itself as simple and still a work in progress, and `brute` also presenting as a lightweight ECS. For your project, that argues for building your own ECS storage model around your exact hot loops instead of inheriting somebody else’s entity semantics too early.[^2_14][^2_15]

I would structure it this way:

- Facts store: archetype-ish or sparse-set-ish component storage in primitive arrays, byte buffers, or direct buffers, with entities as opaque integer ids.
- Clojure layer: scheduling, system composition, resource graph, asset metadata, simulation orchestration.
- Java interop escape hatches: tiny focused classes for the hottest loops, especially meshing, culling, and broadphase-like passes.

That lets Clojure remain literature at the orchestration layer while the hottest contracts are enforced in data layout, not in ideology.

## Voxels and orbital mechanics

For voxels, there does not appear to be an established Clojure-native engine stack to lean on, so chunking, meshing, LOD, paging, and visibility should be treated as first-class engine subsystems you own. For orbital mechanics, the same principle applies even more strongly: your simulation model is domain code, not something you should try to outsource to a generic game library.[^2_16]

A practical split would be:

- `domain.orbit.*`: pure orbital state transitions, reference frames, integrators, admissibility rules.
- `domain.voxel.*`: chunk metadata, residency, meshing decisions, paging policy.
- `shape.*`: transforms between orbital/voxel data and render packets.
- `infra.gl.*` or `infra.bgfx.*`: buffers, shader compilation, command submission.
- `law.*`: contracts for component shapes, world snapshots, shader inputs, chunk residency.

That shape preserves autonomy. It also means you can profile reality before deciding where to collapse into Java or Panama-style lower-level interop later.

## HumbleUI role

Since you are comfortable starting from pieces and performance is king, I would demote HumbleUI from “interface layer” to “optional outer shell” for tooling, launchers, inspectors, and offline editors. The immediate-mode UI path exposed through Nuklear is much more obviously compatible with an engine that wants to own the frame loop and GPU contract from end to end.[^2_7][^2_4]

So my recommendation becomes sharper now:

- **Renderer**: LWJGL + OpenGL first.[^2_2][^2_1]
- **Math**: JOML.[^2_8][^2_6]
- **ECS**: custom.
- **Voxel pipeline**: custom.
- **Orbit simulation**: custom.
- **Tool UI**: Nuklear in-engine; HumbleUI only for non-hot-path tooling if it proves useful.[^2_4][^2_7]

That is the path most aligned with your stated preferences and the actual ecosystem landscape, because it avoids premature dependency on thinly adopted abstractions while still exploiting the strong JVM/native interop surface that does exist.[^2_6][^2_16][^2_2]

### 2.1 Proposed core vocabulary

**Claim**

(defrecord Claim

- Guarantee: any retrieved data passed validation once.

That’s a classic “data‑oriented index” and plays well with Clojure: vector for dense scanning, map for point lookup. It’s also a perfect place to anchor clj‑kondo + Malli contracts.

Clojure shape:

```clojure
(defrecord Registry
  [resource-contract  ;; Contract
   items              ;; vector of resources
   index])            ;; {id -> idx}
```

Laws:

- All `items` conform to `resource-contract`.
- `index` is left-inverse of `items` (no dangling ids).

You can use this uniformly for:

- Entities
- Components (per system)
- Shapes
- Contracts
- Systems
- Snapshots (per store)

That uniformity will pay off as you build out tools.

## 6. Law vs Domain vs Infra: mapping to namespaces

Your axioms already match the house rules; mapping them explicitly:

- `shape.*`
    - `shape.core` – `Shape`, `Claim`, `Event`, `Snapshot`, `Store`, `Registry` data records \& constructors.
    - Pure helpers that don’t know domain semantics.
- `law.*`
    - `law.contract` – combines `Shape` + schema + validate; records violations.
    - `law.ledger` – hashing, Merkle DAG structure, “all state derivable from ledger” checks.
    - `law.registry` – registry invariants.
    - `law.system` – system invariants, tick admissibility.
- `domain.*`
    - `domain.ecs` – system scheduling, `tick` orchestration over multiple systems.
    - `domain.orbit`, `domain.voxel`, etc. – pure(ish) math \& rules about orbital mechanics, chunking, etc.
- `infra.*`
    - `infra.gl` / `infra.webgl` – buffer upload, shader compilation, frame loop.
    - `infra.persistence` – ledger storage, snapshot persistence.
    - `infra.input` – keyboard/mouse/controller events reified into `Event`s.

Infra “speaks” in domain morphisms: e.g. infra.gl calls `domain.render/build-draw-commands` from the current Snapshot and then pushes them to GPU.
