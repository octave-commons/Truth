## High-level goal

Expose the SPH density field \( \rho(\mathbf{x}) = \sum m_i W(|\mathbf{x}-\mathbf{x}_i|, h_i) \) to the renderer by:

- Turning SPH parcels into **render-space gas samples** (position, smoothing radius, density, emission color).  
- Splatting those samples into a **persistent 3D froxel texture** via the same SPH kernel you use in `domain.hydro`.  
- Ray-marching that texture with `volume-program` to get continuous bodies: isolated parcels render sphere-ish, overlapping parcels merge into continuous lobes. 

The result is a clean data flow: ECS → domain SPH → render-space gas field → volume shader.

***

## Data flow overview

You already have most of the building blocks:

- **SPH kernel and smoothing length** in `domain.hydro` (`kernel`, `kernel-r2`, `sph-density`, `smoothing-length`, `gas-structure`).   
- **Volume shader and froxel pipeline** in `infra.render` (`volume-program`, `gas-points`, `build-volume-texture`, `frame-volume`, `render-volume`). 

Path 2 is really “tighten the bridge”:

1. Domain: expose a **stable, pure gas-field API** (SPH-based) for infra to consume.
2. Infra: make the **volume builder** clearly depend on that API (no ad-hoc kernels), with a composable pipeline: samples → froxel grid → texture → volume pass.
3. Rendering: plug the volume into `render-scene` as the first pass.

***

## Step 1 – Domain-level SPH field API

You already have:

- `cubic-spline-w`, `kernel-r2`, `kernel` and `sph-density` for mass-weighted density.   
- `gas-structure` which returns `[[eid density radius] ...]` for nebula parcels, using neighbor cache or spatial index. 

Refine this into a minimal API that infra can call:

1. **Public “gas samples” function** in `domain.hydro`:

   - Signature:  
     ```clojure
     (defn gas-samples
       "Pure SPH gas field projection for rendering: returns
        [{:eid :position :smoothing-h :density :temperature :ionization} ...]."
       [world])
     ```
   - Implementation:
     - Reuse `gas-structure` or mirror its logic: for each `:nebula` / `:protostar` entity, compute:
       - `:position` from `c/position`.
       - `:smoothing-h` from `smoothing-length` or `:radius` (which you already set to \( h/2 \)). 
       - `:density` from `sph-density` / `sph-density-from-cache`.
       - `:temperature` and `:ionization` (`c/temperature`, `c/ionization-fraction`).
     - Keep it **pure**: no GL, no side effects. Just a vector of maps.

2. **Contracts in `law/`**:

   - Define a Malli schema for a “gas sample” (`[:map [:position vec3] [:smoothing-h double] [:density double] ...]`).
   - Add spec/tests that:
     - Verify density normalization (sum over neighbors vs expected ρ).  
     - Check `smoothing-length` behavior (isolated parcel → fallback to radius, non-isolated → \( h \propto d_{nn} \)). 

This gives infra a well-typed handle on the SPH field without leaking ECS details.

## Step 2 – Render-space gas sampling (world → render coords)

Your current `gas-points` in `infra.render` is the right shape: it turns ECS entities into render-space gas samples (position, smoothing support, density norm, color) and uses `temp-color` plus ionization tint. 

Refactor it to consume the **domain API**, not ECS directly:

1. **Move ECS access out of `gas-points`**:

   - Instead of `(ecs/entities-with world ...)`, call `domain.hydro/gas-samples`.
   - Transform each sample via `units/world->render` and `units/phys->render-radius`:

     ```clojure
     {:p   (units/world->render ctx position)
      :h   (units/phys->render-radius ctx smoothing-h)
      :col (temp+ionization-color temperature ionization)
      :dens (nebula-density-norm density)}
     ```

2. **Color mapping is composable**:

   - Keep `temp-color` as is. 
   - Make `temp+ionization-color` a pure function so you can test “hot plasma vs cold gas” visual logic in `law.stellar` or a render-law namespace.

3. **Visual vs physical support**:

   - Decide whether `:h` is exactly the SPH `h` or a scaled visual support (e.g. `visual-h = k * h`) to ensure overlap. This scaling factor is a single knob in `infra`, not embedded in domain.

Now the volume pipeline sees a stable vector of `{p h col dens}` objects derived from the SPH field.

## Step 3 – Froxel grid allocation and cache

Your `volume-cache` / `volume-storage!` already implement a persistent RGBA16F 3D texture and host arrays keyed by resolution. 

Make that the **only owner** of GPU texture and host buffers, and keep it composable:

1. **Volume storage as a record / map**:

   - You already return `{:res R :tex tex :data data :buf buf}`. 
   - Treat this as the “froxel grid resource,” and use it as input to splat functions.

2. **Adaptive resolution selection**:

   - You have `froxel-resolution-for world quality` that uses gas point counts and a quality keyword. 
   - Switch its input to `gas-samples` count rather than ECS count, so any future gas representation still drives resolution correctly.

3. **Domain/infra boundary**:

   - `volume-storage!` stays in `infra.render` (OpenGL + buffers).  
   - Domain only sees the SPH field; it never sees the texture.

## Step 4 – SPH kernel-based splatting into the grid

The heart of Path 2 is splatting SPH parcels into a froxel grid using the kernel \( W(r, h) \). In `build-volume-texture` you already do a radial weight `w = (1 - q)^2` with `q = r^2 / h^2` as a smooth falloff. 

Refine this to be explicitly SPH:

1. **Use `domain.hydro/kernel-r2`**:

   - Instead of the inline `u = (1 - q); w = u^2` fallback, call `kernel-r2` with `r2` and `h` to get physically consistent weights (normalized over volume). 
   - To avoid importing `domain.hydro` directly into `infra.render`, define a small “kernel adapter” in a new `infra.render.field` namespace that depends on domain and exposes a pure `weight(r2 h)` function.

2. **Splat loop structure**:

   - You already:
     - Compute a render-space AABB `[boxMin, boxMax]`.  
     - Derive voxel size (`csx, csy, csz`) from `span / R`.  
     - Loop over `x,y,z` inside the support radius and add contributions to `data[i]`. 

   - Replace the “simple quadratic” falloff with:

     ```clojure
     (let [w (kernel-r2 d2 h)] ; domain kernel
       (let [wd (* w dens)
             i  (idx x y z)]
         (aset data i       (+ (aget data i)       (* wd r)))
         (aset data (inc i) (+ (aget data (inc i)) (* wd g)))
         (aset data (+ i 2) (+ (aget data (+ i 2)) (* wd b)))
         (aset data (+ i 3) (+ (aget data (+ i 3)) wd)))
     ```

   - This ties the render field directly to the physics kernel; density and emission show the same structure SPH “sees.”

3. **Emission vs density separation**:

   - Keep your current layout: `rgb = emission`, `a = density`. 
   - Use `dens` to scale emission (hotter parcels → brighter emission) and keep raw density in alpha.

4. **Optimizations**:

   - **Outlier culling**: you already have `cull-gas-outliers` using median center and 95th percentile radius to avoid huge bounds. 
   - **Bounds padding**: keep the `pad` logic to avoid clipping elongated clouds.
   - **Early exit**: maintain `if (< q 1.0)` guard but now it reflects the true kernel support (outside `r > h`, `kernel-r2` is zero anyway).

This step is where Path 2 really lives: SPH kernel drives texture content.

## Step 5 – Volume frame assembly (volume descriptor)

You already have `frame-volume` which:

- Picks a resolution (`froxel-resolution-for`).  
- Calls `build-volume-texture` and `volume-lights`.  
- Returns `{:tex :box-min :box-max :program :lights}`. 

Make it the **single composable “volume descriptor” builder**:

1. **Use domain API for gas count**:

   - Feed `gas-samples` into `froxel-resolution-for` for more accurate complexity scaling.
   - Pass the same `gas-samples` into `build-volume-texture`.

2. **Document the descriptor type** in `law/render`:

   - Schema for `volume-descriptor`:
     ```clojure
     [:map
      [:tex int]
      [:box-min [:vector double 3]]
      [:box-max [:vector double 3]]
      [:lights [:vector volume-light]]
      [:program int]]
     ```

3. **Conditional construction**:

   - If `gas-samples` is empty, `frame-volume` returns `nil`.  
   - `render-scene` then simply skips the volume pass.

## Step 6 – Ray-march pass integration

Your `render-volume` already does:

- Compute camera basis (`camPos`, `camRight`, `camUp`, `camFwd`).  
- Set uniforms (`boxMin`, `boxMax`, `volume`, `kappa`, `emissionScale`, `scatterScale`, `lights`).  
- Render a fullscreen quad with premultiplied-alpha over the scene. 

Keep this exactly as the “last mile,” driven purely by the volume descriptor:

1. **Volumetric pass at the start of `render-scene`**:

   - You already call `render-volume volume quad-vao camera width height` in `render-scene` before bodies/sprites/HUD. 
   - Ensure all callers of `render-scene` now provide `volume` via `frame-volume`.

2. **Tuning knobs exposed in config**:

   - `kappa`, `emissionScale`, `scatterScale`, and `jitter` become part of a “volume config” that you can adjust for performance and look, without touching SPH or render pipeline semantics.

## Step 7 – Composability and tests

To keep this optimized and composable:

1. **Namespace boundaries**:

   - `domain.hydro`: SPH kernel + gas-samples (pure). 
   - `infra.render.field` (optional): adapters for domain kernels to render weights.
   - `infra.render`: gas → render-space → froxel grid → volume descriptor → volume pass. 
   - `law.render`: schemas for gas samples and volume descriptor, plus property tests.

2. **Epistemic tests**:

   - In `law.render` / tests:
     - Given a simple configuration (one parcel), assert `build-volume-texture` yields a radially symmetric blob centered on its position (within discretization noise).
     - Given two parcels closer than \( 2h \), assert the density ridge merges between them in the froxel grid.
     - Tie SPH density at a point (domain-side) to the sum of froxel densities in a small neighborhood (infra-side) to validate consistency.

3. **Performance knobs**:

   - `froxel-resolution-for` and `cull-gas-outliers` are your main levers; make them configurable via a render-quality profile (low/medium/high/ultra).
