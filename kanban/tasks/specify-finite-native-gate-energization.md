## Context

The human-approved finite milestone is one controlled player reaching one real
Gate through ordinary input, interacting and receiving a visible effect in the
live ECS. Broader progression and civilization are later work. The existing
endpoint card owns historical identity/provenance, while the old native card
verifies fly-resolve-sculpt; neither admits this missing starting-scene and local
operation policy. See `docs/notes/2026-10-08-finite-native-gate-scope.md`.

## Outcome

A reviewed, source-grounded contract for one supported live Spark scene, one
local Gate energization and one actual native acceptance run. The proposal is
`docs/designs/finite-native-gate-energization.md`; it is not executable law.

## Scope

Explicitly choose the player, authored initial-condition provenance, real Gate
identity, physical interaction range, lifetime/clock/scale settings, state/event
owner, ordinary input and visible effect. Separate local energization from
receiver-dependent connection and travel. Derive genuinely small implementation
stories within these boundaries; record exact integration sources and the native
proof contract before code. Coordinate with endpoint UUID
`8e79b9ff-1cd4-4eb9-8a31-80b892fd0c98` without reimplementing its identity model.

## Non-goals

No production change, scenario execution, frozen-fixture acceptance, fabricated
natural prehistory, Gate-discovery reward, biological avatar, civilization
generator, receiver creation, cross-world travel, new ECS/renderer, or enlargement
of the current milestone. No automatic Ready/In Progress transition or merge.

## Acceptance criteria

- Accepted user scope, observed source, proposed game rules and future work are
  distinguishable. Spark control does not claim completed person embodiment.
- Authored initial conditions have explicit origin and run/scenario/device
  identity; they cannot masquerade as simulated technology or construction.
- The scene stays mutable through the existing ECS physics and input path. It
  cannot silently restart into a nebula or use identity ticking.
- Units and a worked approach/release trace connect fixed timestep, displacement,
  interaction range and rendering scale; invalid settings are refused.
- Local energization has one authoritative owner and specifies accepted,
  out-of-range, missing/stale/wrong-run, repeated and malformed outcomes. No
  receiver, travel, cost or reward is inferred from discovery notifications.
- The renderer reads the same device state the interaction writes. Native
  acceptance ties physical approach, ordinary input, one recorded transition
  and visible before/after frames to the same run and device.
- Implementation slices each score at most five points with meaningful RED
  contracts, full repository gates, changed-path performance evidence where
  required, and explicit native verification scope reconciliation.

## Verification

Independent source/design review, current canonical Rheos reads, link and source
identity checks, followed by exact-head planning review through pr-flow. Design
approval supplies no native result and no substitute for later RED/GREEN gates.

## Risks

An attractive static prop can conceal an absent Gate; fabricated prehistory can
conceal absent producers; existing astronomical flight settings can make approach
unplayable. Keep the slice honest and bounded, and expose any real extra dependency
before implementation rather than silently resuming the entire historical ladder.
